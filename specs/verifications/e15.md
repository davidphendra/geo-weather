## Forward-looking: e15s01 real-provider coordinates

Confirmed against OpenWeather docs: Current Weather 2.5 returns `coord: { lat, lon }`. The adapter now
binds it; malformed values (out of range / non-numeric) surface as `WeatherProviderException` → `502`.

## Manual verification script (requires a live OpenWeather key)

Automated tests cannot exercise Leaflet (no browser/JS runtime in the dotnet suite), so confirm the
following by hand:

1. `dotnet user-secrets set "OpenWeather:ApiKey" "<key>" --project src/Weather.WebUI`
2. `dotnet run --project src/Weather.WebUI`
3. Open `/`; select a country and city.
4. Confirm a **Surface Location Map** section appears directly under the 5-day forecast, with OpenStreetMap
   tiles centred on the city and a marker at its coordinates.
5. Click the marker: the popup shows `City, Country — °C / °F` (plain text).
6. Confirm the hero card's `Lat`/`Lon` match the map centre.
7. Select a different city: the map recentres without a second tile grid (no duplicate map).
8. Open the browser console: no CSP violations.
9. Navigate to `/favorites`: no Leaflet or tile requests (lazy load is page-scoped).
10. Remove the key (or block `tile.openstreetmap.org`): the page still renders; the map section shows
    "Map not available — coordinates only." when the API returns no coordinates.

## Offline guarantee

Every new dotnet test uses stub `HttpMessageHandler`s, the `WeatherHostFactory` in-memory server, or pure
domain/value-object assertions. No test performs a live network call. Leaflet and the OSM tiles are loaded
only in a browser at runtime (ADR-0018), outside the offline test gates.

## Known gaps

- Leaflet behaviour (lazy CDN load, marker, popup, dispose, `setView`) is verified manually, not by the
  dotnet suite; there is no bUnit/JS runtime in the test projects.
- The style-parity Playwright harness (`npm run parity:styles`) was not re-run for e15; its probes
  (header, footer, query card, primary button, select) do not touch the map.
